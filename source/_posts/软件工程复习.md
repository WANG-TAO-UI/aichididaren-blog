## 1 · 软件工程基础

### 1.1 软件与软件危机

| 项目 | 必背内容 |
| --- | --- |
| 软件 | 计算机系统中与硬件相互依存的**逻辑部分** = 程序 + 数据 + 相关文档（习题 1-选择 2 答案 D）。硬件是物质产品，软件是逻辑产品，这是最大区别。 |
| 软件危机定义 | 软件开发与维护过程中遇到的一系列严重问题。注意：软件工程是为解决危机而提出的，强调学科产生的历史必然性；说「已成功解决软件危机」过于绝对（习题 1-选择 3 答案 B）。 |
| 主要表现 | ① 成本与进度估计不准，超期超预算；② 用户对交付软件不满意；③ 质量差、可靠性难保证；④ 可维护性差；⑤ 软件费用占系统总成本比例上升；⑥ 生产率跟不上应用普及；⑦ 复用程度低、手工作坊式开发。 |
| 产生原因 · 客观 | 软件是逻辑实体、规模大、复杂度高、难以度量与可视化；维护本身会不断引入新需求。 |
| 产生原因 · 主观 | 缺乏工程化方法与项目管理；忽视需求分析；轻视文档与维护；用户与开发者沟通不畅；个人技艺式开发。 |

### 1.2 软件工程的含义与内容

| 项目 | 必背内容 |
| --- | --- |
| 含义 | 把工程化的原则、方法、技术与管理应用于软件的开发与维护，以合适的成本生产满足用户需要、可用性好的产品。 |
| 目标 | 成本合适 + 满足需求 + 可用性 / 质量好，三者兼顾（习题 1-选择 4 答案 C）。 |
| 内容 | 软件开发技术（**方法 · 工具 · 环境**，习题 1-填空 3）＋ 软件工程管理（计划、组织、控制、质量保证）。 |
| 层次结构 | 自底向上：工具层 → 方法层 → 过程（管理）层 → 质量保证层（习题 1-填空 4）。 |

### 1.3 软件生命周期

| 时期 | 阶段 | 基本任务 | 主要产出 |
| --- | --- | --- | --- |
| 定义期 | 计划 | 问题定义（要解决什么问题）＋ 可行性研究（技术 / 经济 / 操作是否可行） | 可行性研究报告、项目计划 |
| 需求分析 | 确定功能、性能、约束与接口，回答「做什么」 | 需求规格说明书 SRS |
| 开发期 | 设计 | 概要设计（体系结构、模块划分、接口）＋ 详细设计（模块内算法与数据结构） | 概要 / 详细设计说明书 |
| 编码 | 写出正确、易理解、易维护的程序模块 | 源程序、单元测试用例 |
| 测试 | 单元 → 集成 → 系统 → 验收，使软件达到预定要求 | 测试报告 |
| 交付 | 安装、培训、试运行 | 用户手册、交付版本 |
| 运行维护期 | 运行维护 | 改错、适配环境、扩充功能、预防性重构，使系统持久满足需求 | 维护记录、变更登记 |

**两个必考数字：**测试与排错约占开发总工作量 **40%**（习题 1-选择 5）；**维护阶段**时间最长、花费最多（习题 1-选择 6、8-选择 8/9，费用高的根本原因是维护生产率低）。

### 1.4 软件工程基本原理（简答题必背 7 条）

1.  用**分阶段的生命周期计划并严格管理**；
2.  坚持进行**阶段性评审**；
3.  实行**严格的产品控制**（变更控制 / 配置管理）；
4.  采用**现代程序设计技术**；
5.  结果应能**清楚地审查**（可追溯、可验证）；
6.  开发小组人员应**少而精**；
7.  承认**不断改进**软件工程实践的必要性。

**记忆口诀：计 · 评 · 控 · 技 · 审 · 人 · 改。**考场上先默写七个字，再逐条扩成一句话，绝不会漏点。

## 2 · 开发模型：瀑布 vs 快速原型

| 维度 | 瀑布模型 | 快速原型模型 |
| --- | --- | --- |
| 过程 | 需求分析 → 设计 → 编码 → 测试 → 运行维护，线性单向、阶段严格划分、文档驱动，前阶段评审通过才进下一阶段 | 收集基本需求 → 快速构造可运行原型 → 用户试用反馈 → 修改原型（循环）→ 确认需求 → 正式开发 |
| 核心特点 | 将开发过程严格划分为一系列有序的活动（习题 1-选择 7 答案 A） | 以原型为中介，让用户在早期就看见并试用系统 |
| 需求前提 | 需求明确且稳定 | 需求模糊、用户说不清想要什么 |
| 优点 | 易管理、阶段可评审、文档规范、技术成熟 | 需求准确、用户参与度高、不确定性与风险早暴露 |
| 缺点 | 缺乏灵活性、风险暴露晚、返工代价大、用户后期才见到产品 | 易牺牲质量与文档、原型被误当成品、范围与进度难控 |
| 适用 | 需求稳定的成熟领域、中小型项目 | 交互性强、探索性的新系统 |

补充（习题 1-思考 4）：增量模型＝分批交付、早期见效；螺旋模型＝瀑布 + 原型 + 风险分析，适合大型高风险项目；喷泉模型＝面向对象、迭代无缝、阶段重叠。本题只需记前两个。

## 3 · 面向对象三大模型 全卷第一重点

框架来自 **OMT**（Rumbaugh 等，1991）：把分析收集到的信息构造在对象模型、动态模型、功能模型中；开发分「系统分析 → 系统设计 → 对象设计 → 实现」四阶段（习题 4-选择 2）。

| 模型 | 对应图形 | 主要功能 | 回答什么问题 / 关键词 |
| --- | --- | --- | --- |
| 对象模型 | **类图**（含对象图） | 描述系统的**静态结构**：类、属性、操作，以及类间关联、泛化、聚合、依赖与多重性 | 系统由什么组成 / 静态 · 结构 |
| 动态模型 | **状态图**、**时序图**（顺序图 / 协作图） | 描述**控制结构与交互顺序**：一个对象生命周期中的状态序列、事件触发的迁移、对象间消息的时间先后 | 何时、按什么顺序发生 / 行为 · 时序 |
| 功能模型 | **用例图** | 描述**系统应提供的功能**：参与者、用例、系统边界，从用户视角刻画系统服务 | 系统为谁做什么 / 需求 · 用户视角 |

**简答题「三个模型的主要功能」标准结构：**每个模型写四段 ——「模型名 → 对应图 → 描述什么 → 回答什么问题」，三段并列，最后加一句「三者分别从结构、行为、功能三个视角互补地刻画系统」。

**易错辨析（题库原话）：**

+   用例图从程序员角度描述系统功能 → **×**，是参与者（用户 / 外部系统）视角【习题 2-判断 2】；
+   对象图描述类的动态结构 → **×**，类图与对象图都是静态图，对象图只是某一时刻的实例快照【习题 2-判断 3】；
+   状态图属动态视图；活动图与状态图都描述动态行为；顺序图与协作图语义等价、可互相转换【习题 2-选择 2 / 选择 7】；
+   复杂系统必须从多视角多模型描述，「一个重要系统用一个模型就够」违背建模基本原则【习题 2-选择 5】。

## 4 · 面向对象基本概念与设计原则

| 概念 | 一句话定义（名词解释可直接用） | 习题印证 |
| --- | --- | --- |
| 对象 | 封装了属性（状态）、方法（行为）并能响应事件的运行时实体；对象 = 数据 + 操作，通过消息与外界交互 | 对象三要素：属性 / 方法 / 事件【7-选择 2】 |
| 类 | 具有相同属性和操作的一组对象的抽象模板；扩展了传统数据类型——除取值范围外还定义操作，并支持继承与多态 | 类是模板，对象是实例【4-思考 2/4】 |
| 封装 | 把数据与对数据的操作捆绑在一起，隐藏内部实现，只通过公开接口对外提供服务 | 消息是对象与外界相互联系的唯一途径【1-填空 5】 |
| 模块化 | 把系统分解为若干独立命名、可独立编址、功能单一的模块；划分标准就是高内聚低耦合 | 详细设计原则【6-简答 2】 |
| 高内聚低耦合 | 模块内部各元素联系紧密、只做一件事（高内聚）；模块之间依赖尽可能少、接口尽可能简单（低耦合） | 结构优化启发式规则【5-思考 1】 |
| 信息隐藏 | 模块内部实现细节对其他模块不可见，使修改局部化，从而提高可理解性、可测试性与可维护性 | 可维护性子特性【8-简答 9/10】 |
| 复用 | 重复使用已有的类、构件、设计模式与领域模型，减少重复开发、提高质量与一致性 | 【1-思考 6 面向对象优点】 |

#### 类 vs 对象（三层差别）

| 比较 | 类 | 对象 |
| --- | --- | --- |
| 本质 | 抽象模板 / 类型定义 | 类的一个实例 |
| 属性值 | 只定义属性名与类型，无具体值 | 有各自的具体属性值 |
| 存在期 | 设计期 / 编译期存在 | 运行期存在；一个类可实例化出多个对象 |

封装*→*信息隐藏*→*低耦合*→*易修改 / 易测试*→*易复用 · 易维护

这条链同时是习题 6-简答 2（详细设计原则）、习题 8-简答 9（可维护性衡量）、习题 8-简答 10（提高可维护性的措施）的共同答案骨架。

## 5 · 需求分析与建模

**铁律：**需求分析只回答「**系统必须做什么**」，不回答「怎么做」【习题 3-填空 7】。凡把算法写进需求陈述都算跑题。

### 5.1 需求陈述的四项内容

| 项 | 要写什么 |
| --- | --- |
| 问题域范围 | 系统边界、业务背景、参与者与涉及部门、与其他系统的接口 |
| 功能需求 | 系统必须完成的全部功能：输入 → 处理 → 输出，以及异常处理 |
| 性能需求 | 响应时间、吞吐量、精度、并发、安全性、可靠性、数据完整性 |
| 应用性探讨 | 可行性、运行环境与约束、假设条件、将来可能的变化与扩展 |

### 5.2 获取需求的非正式方法

访谈 / 用户座谈（最常用）· 问卷调查 · 现场观察与跟班作业 · 查阅业务文档、单据、报表 · 原型演示并收集反馈 · 头脑风暴 / 联合需求计划 JRP。特点：灵活、成本低、依赖分析员沟通能力，需配合正式评审来确认。

### 5.3 结构化分析（SA）与数据流图

| 要点 | 内容 |
| --- | --- |
| SA 基本步骤 | **自顶向下**逐层分解系统 → 画分层数据流图 → 由后向前定义数据与加工 → 编数据字典与加工说明 → 写需求规格说明书 SRS【习题 3-填空 3】 |
| 三大描述工具 | 数据流图 DFD（功能模型）· 数据字典 DD（数据模型）· 加工说明（结构化语言 / 判定表 / 判定树）。**程序流程图不属于 SA**，它是详细设计工具【习题 3-选择 2】 |
| DFD 四要素 | 外部实体（矩形）· 加工（圆角框 / 圆圈，带编号）· 数据流（箭头，必须标名称）· 数据存储（双线 / 开口矩形） |
| 画法规则 | 顶层图把整个系统当作一个加工；逐层分解至不可再分；父子图编号一致、**数据流平衡**；每个加工至少一进一出 |
| 数据字典（了解） | 对 DFD 中所有数据流、数据元素、数据存储、加工的定义集合，是 DFD 的补充词典 |
| 需求评审闭环 | 规划 → 准备 → 评审会议 → 修改缺陷 → 重审【习题 3-填空 4】 |

### 5.4 ER 图三要素（设计题第 ② 步）

| 符号 | 含义 | 注意 |
| --- | --- | --- |
| 矩形框 | 实体 | 从需求陈述中用「名词法」抽取，如 读者、图书、借阅记录 |
| 椭圆 | 属性 | 主键加下划线；属性不能画成实体 |
| 菱形 | 实体间联系 / 关系 | 连线两端必须标注 1:1 / 1:n / m:n 基数 |

## 6 · 测试 必考

### 6.1 按开发时间线分类

| 阶段 | 测什么 | 主要方法 | 备注 |
| --- | --- | --- | --- |
| 单元测试 | 模块接口、**局部**数据结构、所有独立执行路径、错误处理通路、边界条件 | 白盒为主 | 不含「全局数据结构」【8-选择 6】 |
| 集成测试 | 模块间接口、组装后的交互与数据传递 | 白盒 + 黑盒 | 自底向上 / 自顶向下 |
| 系统 / 事务 / 确认测试 | 整体功能、性能、安全性与需求符合性 | 黑盒为主 | 见下方表述差异说明 |
| 验收测试 | 按合同 / 用户需求验证，用户参与 | 黑盒 | 交付决策依据 |
| 回归测试 | 修改或维护后重测，确认未引入新错误 | 复用既有用例 | 贯穿全程，不是最后一站；维护副作用 = 因修改造成的新错误【8-选择 12】 |

**表述差异提醒：**复习重点写「事务测试」，题库 8-选择 4 写「系统测试」，教材常写「确认测试」——三者指同一层级。考场上写「**系统（确认 / 事务）测试**」并补一句说明最稳。标准顺序为 单元 → 集成 → 系统 → 验收【答案 A】。

### 6.2 白盒测试 vs 黑盒测试（必考对比表）

| 维度 | 白盒测试 | 黑盒测试 |
| --- | --- | --- |
| 别称 | 结构测试、玻璃盒测试 | 功能测试、数据驱动测试 |
| 设计依据 | 程序内部逻辑与源代码结构 | 需求规格说明书（不看代码） |
| 视角 | 看得见盒子内部，已知实现 | 把程序当不透明盒子，只看输入 / 输出 |
| 关注点 | 内部逻辑、路径、分支是否被执行【8-选择 1 答案 A】 | 功能是否符合需求、结果是否正确 |
| 常用方法 | 逻辑覆盖（语句 → 判定 → 条件 → 判定-条件 → 条件组合 → 路径）、基本路径测试 | 等价类划分、边界值分析、错误推测、因果图 / 判定表 |
| 主要阶段 | 单元测试、集成测试 | 系统（确认 / 事务）测试、验收测试 |
| 擅长发现 | 逻辑错误、未覆盖路径、死代码 | 功能遗漏、接口与输入输出错误、界面错误 |
| 局限 | 查不出「功能根本没做」 | 无法保证内部路径都被走到 |

### 6.3 白盒：逻辑覆盖强度阶梯

语句覆盖*<*判定覆盖*<*条件覆盖*<*判定—条件覆盖*<*条件组合覆盖*<*路径覆盖

**最弱是语句覆盖**（只要求每条语句执行一次，连分支真假都不保证）【习题 8-选择 3 答案 C】。基本路径测试：由控制流图计算环形复杂度 → 导出独立路径集合 → 为每条路径设计用例。

### 6.4 黑盒：等价类划分

把输入域划分为若干**有效等价类**与**无效等价类**，每类只取一个代表值；优：用例少覆盖广；缺：边界处易漏。示例：成绩要求 0 ≤ x ≤ 100 的整数。

| 等价类 | 输入范围 | 代表数据 | 预期 |
| --- | --- | --- | --- |
| 有效等价类 | 0 ≤ 成绩 ≤ 100 的整数 | 50 | 接受 |
| 无效等价类 ① | 成绩 < 0 | \-1 | 拒绝并提示 |
| 无效等价类 ② | 成绩 > 100 | 101 | 拒绝并提示 |
| 无效等价类 ③ | 非数字 / 非整数 | "abc" | 拒绝并提示 |

### 6.5 黑盒：边界值分析（相同 / 高于 / 低于，三种情况各取一组数据）

| 三种情况 | 测试数据 | 覆盖的边界 | 预期输出 |
| --- | --- | --- | --- |
| 等于边界（相同） | 0、100 | 下界值与上界值本身 | 正常接受 |
| 低于边界 | \-1（即 0 − 1） | 刚好低于下界 | 拒绝，提示超范围 |
| 高于边界 | 101（即 100 + 1） | 刚好高于上界 | 拒绝，提示超范围 |

更严谨的七点法：-1、0、1、50、99、100、101。答题先写「三种情况各一组」，再补七点法最稳。等价类管「区间内代表」，边界值专打「区间两端」，两者互补。

### 6.6 测试的补充结论（题库高频）

+   测试是「为了发现错误而执行程序的过程」，**只能证明有错，不能证明无错**【8-简答 1】。
+   造成软件缺陷的最主要原因是**需求说明书**【8-选择 5】；越晚发现，修复成本越高。
+   测试 vs 调试：测试是显示错误、可预期可控；调试是推理排错过程，需经验与想象。调试后必须做回归测试【8-选择 7、简答 6】。
+   四种黑盒方法优缺点、白盒方法清单见习题 8-简答 3 / 简答 4。

## 7 · 图形区分：题目要求哪种就画哪种

| 题干关键词 | 该画的图 | 核心符号 |
| --- | --- | --- |
| 「谁使用系统」「系统提供哪些服务」 | 用例图（功能模型） | 小人＝参与者，椭圆＝用例，矩形框＝系统边界 |
| 「有哪些类 / 属性 / 方法」「类间关系」 | 类图（对象模型，静态结构） | 三层矩形＝类名 / 属性 / 方法，实线＝关联 + 多重性 |
| 「对象经历哪些状态」「事件触发」 | 状态图（动态模型） | 圆角框＝状态，箭头＝迁移，标「事件 \[条件\] / 动作」；起点实心圆、终点牛眼 |
| 「实体、属性、实体间联系」「1:n」 | ER 图（数据建模） | 矩形＝实体，椭圆＝属性（主键下划线），菱形＝联系 + 基数 |

**四个常见扣分点：**① ER 图里画了「方法」或类图里画了菱形（图形体系混用）；② 实体漏主键、联系漏标基数；③ 把「借阅日期」这类联系的属性误当独立实体，或 m:n 未用中间实体分解为两个 1:n；④ 题目要求 ER 图却顺手又补了用例图 / 类图（多画同样扣分）。

## 8 · 设计题完整演示：需求 → ER 图 → 类图

### 题目（模拟真题）

某高校图书馆拟开发图书借阅管理系统。读者持借书证（借书证号、姓名、读者类型、可借册数）可查询图书并办理借书、还书；每本图书有 ISBN、书名、作者、出版社、馆藏册数；每次借书产生一条借阅记录（记录号、借出日期、应还日期、实际归还日期、是否逾期）。一个读者可借阅多本图书，一本图书可被多名读者先后借阅。管理员负责办理借还手续并维护信息。要求响应时间 ≤ 2 秒、支持 200 并发、借阅数据不得丢失。  
**要求：按「需求 → ER 图 → 类图」顺序作答。**

### 第 ① 步 · 需求陈述与要素抽取

| 项 | 内容 |
| --- | --- |
| 问题域范围 | 图书馆借还业务；边界 = 查询 / 借书 / 还书 / 信息维护；参与者 = 读者、管理员 |
| 功能需求 | 图书查询、借书、还书、逾期判定、读者与图书信息维护 |
| 性能需求 | 响应 ≤ 2 s、并发 200、数据完整不丢失 |
| 应用性探讨 | 与校园一卡通对接、运行环境、后续可扩展预约功能 |

**名词法抽实体：**读者、图书、借阅记录（管理员属参与者，若题目要求可补为实体）。

| 实体 | 属性 | 主键 |
| --- | --- | --- |
| 读者 | 借书证号、姓名、读者类型、可借册数 | 借书证号 |
| 图书 | ISBN、书名、作者、出版社、馆藏册数 | ISBN |
| 借阅记录 | 记录号、借出日期、应还日期、实际归还日期、是否逾期 | 记录号 |

| 关系 | 基数 | 处理 |
| --- | --- | --- |
| 读者 — 图书（借阅） | m:n | 用中间实体「借阅记录」分解为两个 1:n |
| 读者 — 借阅记录（产生） | 1:n | 一个读者可有多条借阅记录 |
| 图书 — 借阅记录（对应） | 1:n | 一本图书可出现在多条记录中 |
| 管理员 — 借阅记录（办理） | 1:n | 可选补画 |

### 第 ② 步 · ER 图（Chen 表示法）

矩形＝实体，椭圆＝属性（主键加下划线），菱形＝联系，连线标注 1 / n 基数。

图书借阅系统 ER 图读者、借阅记录、图书三个实体及属性，通过产生与对应两个菱形联系连接并标注基数。 借书证号 姓名 可借册数 ISBN 书名 馆藏册数 读者 借阅记录 图书 产生 对应 1nn1 记录号 借出日期 应还日期 是否逾期 ① 下划线＝主键；矩形是实体、椭圆是属性、菱形是联系，三者别混 ② 读者与图书本是 m:n，用「借阅记录」实体分解成两个 1:n（图上已标 1 / n） ③ 其余属性（作者、出版社、实际归还日期等）按同法补椭圆即可

### 第 ③ 步 · 类图

| ER 图元素 | → 类图元素 | 说明 |
| --- | --- | --- |
| 实体（矩形） | 类（三层矩形） | 类名 / 属性 / 方法，三层缺一不可 |
| 属性（椭圆） | 带类型的属性 | 如 `- ISBN : String`；- 私有，+ 公有 |
| 联系（菱形） | 关联（实线）+ 多重性 | 1、0..1、1..\*、\* |
| 主键 | 标识属性 | 可标注 «PK» 或在属性后注明 |
| （无） | 方法 / 操作 | **类图必须补，ER 图绝对不画** |

类图：三层矩形 + 实线关联 + 多重性标注；「借阅记录」为分解 m:n 得到的关联类。

图书借阅系统类图读者、借阅记录、图书、管理员四个类，含属性方法与关联多重性。 读者 \- 借书证号 : String\- 姓名 : String\- 可借册数 : int\+ 查询图书()\+ 借书() / 还书() 借阅记录（关联类） \- 记录号 : String\- 借出日期 : Date\- 应还日期 : Date\- 是否逾期 : boolean\+ 计算逾期()\+ 归还登记() 图书 \- ISBN : String\- 书名 : String\- 馆藏册数 : int\+ 借出() / 归还()\+ 查询馆藏() 管理员 \- 工号 : String\- 姓名 : String\+ 办理借还()\+ 维护信息() 10..\*0..\*10..\*1 产生对应办理 ER → 类图：实体→类　属性→带类型的属性　联系→关联 + 多重性　主键→标识属性 关键差别：类图必须补「方法」并有三层矩形；ER 图绝不画方法

### 设计题六步检查清单

+   需求陈述四项（范围 / 功能 / 性能 / 应用性）是否都写了？
+   实体是否用名词法抽全？属性是否漏主键、主键是否加下划线？
+   每个联系是否标了 1:1 / 1:n / m:n？m:n 是否已分解为两个 1:n？
+   ER 图是否只用矩形 / 椭圆 / 菱形，且没有出现「方法」？
+   类图是否三层矩形齐全（类名 / 属性 / 方法），并补了关联与多重性？

## 10 · 名词解释速记卡

**软件危机**

软件开发与维护过程中遇到的一系列严重问题，本质是规模与复杂度增长超出手工作坊式开发的能力。

**软件工程**

把工程化原则、方法、技术与管理用于软件开发维护，以合适成本生产满足需求、可用性好的产品。

**软件生命周期**

软件从计划、需求分析、设计、编码、测试到运行维护直至退役的全过程，分定义期、开发期、运行维护期。

**瀑布模型**

线性顺序、阶段严格划分、文档驱动的开发模型，前阶段评审通过才进入下一阶段。

**快速原型模型**

快速构建可运行原型，经用户试用反馈反复修改以确认需求，再正式开发。

**对象**

封装了属性、方法并能响应事件的运行时实体，通过消息与外界交互。

**类**

具有相同属性与操作的一组对象的抽象模板，是对象在运行期的实例化依据。

**封装**

把数据与对数据的操作捆绑在一起，隐藏内部实现，仅通过公开接口提供服务。

**模块化**

把系统分解为独立命名、功能单一、可独立编址的模块，划分标准为高内聚低耦合。

**高内聚低耦合**

模块内部元素联系紧密、模块之间依赖尽可能少且接口简单。

**信息隐藏**

模块内部实现细节对其他模块不可见，使修改局部化，提高可维护性。

**复用**

重复使用已有的类、构件、设计模式与领域模型，减少重复开发。

**白盒测试**

已知程序内部逻辑，按代码路径与分支设计用例的结构测试，用于单元 / 集成测试。

**黑盒测试**

不看内部代码，仅依据需求规格检查输入输出是否正确的功能测试，用于系统 / 验收测试。

**等价类划分**

把输入域分为有效 / 无效等价类，每类取一个代表值设计用例的黑盒方法。

**边界值分析**

针对输入边界，取等于边界、略低于边界、略高于边界三组数据的黑盒方法。

**回归测试**

软件修改或维护后重新执行既有用例，确认未引入新错误的测试活动。

**用例图**

从参与者视角描述系统应提供哪些功能的图，由参与者、用例与系统边界构成。
